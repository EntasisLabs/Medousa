# Medousa 0.6.0 — Peer mesh (personal ↔ team)

Daemon↔daemon capability-scoped handoffs. **Not** portal sudo. **Not** same-daemon Shared seats.

## Model

- **Portal** — work *inside* the team brain (workshop switcher).
- **Mesh peer** — personal daemon paired to team for selected handoffs (send note, ask review, bring result home).
- No ambient vault / Locus / identity sync.

## Security bar

1. Mutual daemon identity (long-term keys).
2. Capability grants (`mesh.message`, `mesh.bundle.push`, `task.request`, …).
3. Signed envelopes (sender/recipient/seq/expiry/capability/payload hash).
4. **Iroh ticket = routing only** — never treat proxied Iroh as loopback.
5. Consent + provenance; revoke mesh without killing portal memberships.

### M4 Share (shipped)

Vault/artifact **Share to peer** uses the same path as Peers attach: export bundle → enveloped `peer` message with attachment → recipient auto-import + unread card. Silent-only push is no longer the product path for that sheet. Remote `/v1/share/push` still records mesh inbox + receipt when used.

### M4 Ask (shipped)

Vault/artifact **Ask for review** reuses the Share pipe with `kind: "review_request"` on the peer message (still `mesh.message` — not `CAP_TASK_REQUEST` / `/v1/mesh/ask` yet). Recipient sees a labeled Peers-thread card + auto-import; work-board cards deferred.

### M4 Bring-home (shipped)

Vault/artifact **Bring home** is the reverse Share: same pipe with `kind: "bring_home"` so a peer can send a result back to the requester’s peer door. Labeled Peers-thread card + auto-import; still `mesh.message`.

## M4+ — Daemon as introducer / relay (not STUN)

**Intent:** When two Homes are already doors into the *same* workshop daemon, that daemon can **introduce** them (and optionally **relay** signaling or bytes) so they can find each other — without merging brains or ambient sync.

This is **client ↔ client, introduced by a daemon**. It is **not** mesh mail (daemon ↔ daemon) and **not** portal sudo.

| Piece | Rule |
|-------|------|
| Prerequisite | Both clients paired to D (portal and/or peer) |
| Consent | Explicit introduce / accept — not “everyone online is visible” |
| Capability | Dedicated grant (e.g. `client.rendezvous` / `client.relay`) — not implied by portal alone |
| Payload | Endpoint hints first (device id, Iroh ticket, LAN URL); relay is opt-in and scoped |
| Non-goals | Vault/session sync, elevating peer→portal, treating reachability as trust |

**Why it feels “almost there”:** M3 registry already tracks paired devices + endpoint hints from heartbeat. M4+ adds consent, capability, and a Home UX for “meet / relay via this workshop” without inventing a global inbox.

See [home-messaging-matrix.md](home-messaging-matrix.md#m4--client-rendezvous--relay).

## P0 (blocks mesh)

Gateway injects `X-Medousa-Transport: iroh`. Handlers that skip auth on loopback must ignore that header case — require bearer for remote/proxied traffic.
